# بوابة قبول Staging — Employee Photos

**الفرع:** `security/private-employee-photos`
**الحالة:** `NOT RUN` — لا توجد نتائج Staging في هذه الوثيقة.
**النطاق:** Privacy/Storage Boundary فقط؛ لا يُدمج مع `security/trusted-device-enrollment-hardening` الخاص بـAuthentication Boundary.

> نجاح الاختبارات المحلية لا يُثبت سلوك Supabase Storage الحقيقي. لا يُسمح باعتبار التغيير جاهزًا لـProduction قبل نجاح الاختبارات الأربعة أدناه على نفس نسخة الكود والـMigration المرشحة للنشر.

## متطلبات التنفيذ

- تحديد مشروع Supabase **Staging** منفصل عن Production وتأكيد هويته قبل أي تطبيق أو نشر. المشروع المحدد هو `adwvokwucotohwayorgx`؛ فُحص قراءةً وكان فارغًا، ولم تُطبق عليه الملفات.
- واجهة Staging تستخدم عنوان ومفتاح مشروع Staging فقط، وليس إعدادات Production المضمّنة حاليًا في صفحات المستودع.
- تطبيق الـMigration بعد مراجعة المالك والتحقق من baseline، ثم التوقف للتحقق من Storage/RLS/RPC، ثم نشر `employee-photo-url` والواجهة على Staging. الدالة تعتمد على RPCs الجديدة داخل الـMigration؛ نشر الدالة وحده لا يثبت جاهزية مسار الجهاز.
- موظفان اصطناعيان A وB ببيانات دخول معروفة وصورتين موجودتين بالفعل، دون صور أو بيانات موظفين حقيقيين.
- استخدام جلسة متصفح نظيفة، تعطيل cache في DevTools، وتسجيل إصدار الكود ووقت كل طلب.
- لا يُنشر أي token أو رقم هاتف أو signed URL كامل في تقرير عام. تُسجل الحالات والتوقيتات والأحجام فقط وتُحجب أسرار الأدلة.
- الـsweep يبقى `dry_run`؛ لا حاجة لتشغيل حذف الملفات لإجراء هذه الاختبارات.

## 0 — لا روابط قديمة في البيانات

شغّل بعد تطبيق الـMigration على Staging وقبل أي نشر:

```sql
select count(*) from public.employee_registrations
where employee_photo_url like 'http%';
```

**المطلوب:** `0`.

- قياس الإنتاج قبل التطبيق (2026-10-06): صفان فقط، وكلاهما رابط عام من نفس الـbucket، و**صفر** قيمة غير قابلة للتفسير. لذلك يتوقع أن يصل الفحص إلى 0 تلقائيًا بعد الـbackfill.
- إذا كانت النتيجة أكبر من صفر، فالقيمة من مضيف أو bucket آخر؛ راجعها يدويًا ولا تحذفها آليًا، ووثّق كل صف.
- تحقق أيضًا أن `private.employee_photo_object_path(employee_photo_url) is null` يعطي نفس عدد الصفوف غير المفسّرة، وأن الـMigration طبع تحذيرًا غير مانع عند وجودها.

**النتيجة:** `NOT RUN`.

## 1 — Public URL

**الخطوات:**

1. تأكد أن صورة B موجودة فعليًا؛ اختبار مسار غير موجود مثل `xxx.jpg` لا يُثبت إغلاق الـbucket.
2. بعد الـMigration، اطلب مسارها العام دون Authorization:

```text
https://<STAGING_REF>.supabase.co/storage/v1/object/public/employee-photos/<B_OBJECT_PATH>
```

3. سجّل HTTP status وbody ونوع المحتوى، وتأكد أن الاستجابة جاءت من الشبكة وليس browser cache.

**القبول:** `403` أو `404 / Not Found`، دون إرجاع بايتات الصورة. إذا أعاد مزود الخدمة رمزًا مختلفًا، يُسجل كما هو وتُراجع دلالته؛ لا يُحوَّل تلقائيًا إلى PASS. وجود الصورة يُثبت لاحقًا باختبار Signed URL.

**النتيجة:** `NOT RUN`.

## 2 — Signed URL ثم انتهاء الصلاحية

اطلب صورة A بهوية A الصحيحة:

```json
{
  "action": "resolve",
  "path": "<A_OBJECT_PATH>",
  "actor": {
    "type": "employee",
    "employee_id": "<A_ID>",
    "mobile_number": "<A_PHONE>"
  }
}
```

**القبول الأولي:** HTTP `200`، و`ok: true`، و`expires_in: 60`، ورابط واحد موقّع. افتح الرابط مباشرة قبل الانتهاء وتحقق من عرض الصورة الصحيحة.

**فحص الانتهاء:**

1. احتفظ **بنفس الرابط** الصادر أول مرة وسجّل وقت إصداره.
2. انتظر أكثر من 60 ثانية؛ استخدم 75 ثانية كهامش لفروق التوقيت، لا كتغيير لمدة الرابط.
3. أعد طلب **نفس الرابط القديم** مع تعطيل cache وراقب طلب شبكة جديدًا.
4. لا تطلب رابطًا جديدًا من الـResolver في هذه الخطوة؛ الرابط الجديد له مدة جديدة ولا يختبر انتهاء القديم.

**القبول النهائي:** رفض الطلب القديم بخطأ انتهاء token وعدم إرجاع بايتات الصورة. سجّل HTTP status ورسالة Storage الحقيقية دون افتراض كلمة `Expired` حرفيًا. ظهور صورة محمّلة سابقًا في الصفحة لا يُعد فشلًا أو نجاحًا لاختبار انتهاء طلب جديد؛ ما تم تنزيله سابقًا لا يُسحب من الجهاز بانتهاء الرابط.

**النتيجة:** `NOT RUN`؛ اختبار TTL المحلي ليس اختبار انتهاء HTTP حقيقيًا.

## 3 — IDOR دون كشف سبب الرفض

باستخدام بيانات A الصحيحة، استبدل المسار بمسار B:

```json
{
  "action": "resolve",
  "path": "<B_OBJECT_PATH>",
  "actor": {
    "type": "employee",
    "employee_id": "<A_ID>",
    "mobile_number": "<A_PHONE>"
  }
}
```

**القبول:** HTTP `403` والاستجابة بالضبط:

```json
{"ok":false,"error":"DENIED"}
```

- لا `reason` ولا `NOT_OWNER` ولا URL ولا بيانات عن B.
- كرر الطلب بمسار غير موجود داخل مجلد B: يجب أن تكون الحالة وbody مماثلين.
- صورة A نفسها يجب أن تنجح ببيانات A: حتى لا يُسجل فشل جميع الطلبات باعتباره حماية IDOR صحيحة.
- هذه مساواة في الحالة وpayload، وليست ادعاءً بتساوي أزمنة الاستجابة.

**الدليل المحلي:** جرى توحيد جميع استجابات `403`، واختبار رفض التفويض دون الوصول إلى lookup أو signing. هذا لا يستبدل اختبار Staging.

**النتيجة:** `NOT RUN`.

## 4 — Upload حقيقي من المتصفح

استخدم صفحة تسجيل Staging مع بيانات اصطناعية. لكل ملف سجل: عدد بايتاته، `File.type`، `Content-Type` المرسل، HTTP response، وهل أنشئ object فعليًا. إذا رفضته الواجهة قبل إرسال الطلب فسجل ذلك صراحةً، ولا تصفه بأنه رفض من الخادم.

**الحد الفعلي:** `2 MiB = 2,097,152 bytes`، وليس `2,000,000 bytes`. قبول ملف عند الحد يعني قبول **الحجم الكامل للملف** لا أبعاد الصورة.

| الملف | المطلوب | النتيجة |
|---|---|---|
| JPG صالح بحجم 1 MiB | قبول الرفع وتخزين object path فقط | NOT RUN |
| PNG صالح بحجم 2,097,152 bytes | قبول الملف عند الحد بالضبط | NOT RUN |
| SVG | رفض؛ لا object جديد | NOT RUN |
| EXE معاد تسميته إلى JPG | رفض المحتوى غير الصوري؛ لا object جديد | NOT RUN |
| صورة صالحة بحجم 3 MiB | رفض تجاوز الحد؛ لا object جديد | NOT RUN |

### نقطة مفتوحة: EXE مع MIME مزور

التنفيذ الحالي يفحص الامتداد و`File.type`/MIME والحجم؛ **لا يفحص magic bytes ولا يفك ترميز الصورة على الخادم**. هذه الشروط لا تثبت رفض ملف تنفيذي يحمل اسم `.jpg` و`Content-Type: image/jpeg`.

ضمن حالة EXE نفسها، اختبر النسخة المعاد تسميتها من File Picker، ثم إعادة إرسال الطلب على Staging مع MIME مزور. يكفي ملف اختبار غير تنفيذي يبدأ بـ`MZ` لقياس الرفض؛ لا حاجة لتشغيل أي ملف أو رفع برمجية ضارة.

إذا قبل Storage المحتوى غير الصوري، فحالة الاختبار `FAIL` وتبقى بوابة Production مغلقة حتى إصلاح موثوق وإعادة الاختبار. إصلاح الواجهة وحده لا يُنشئ حد حماية على الخادم؛ أي تغيير لاحق لمسار الرفع على الخادم يتطلب مراجعة معمارية واضحة. **لم يُنفذ مثل هذا التغيير في هذه المتابعة.**

## 5 — ترويسات Cache للرابط الموقّع

المطلوب: ألا يُخزَّن الرابط الموقّع في أي cache.

**ما هو مضمون في الكود (مُختبر محليًا):** الطلب يُنفّذ بـ`cache: "no-store"` و`credentials: "omit"`، والعرض عبر `blob:`، والرابط لا يُكتب في `localStorage`/`sessionStorage`، وService Worker لا يخزّن أي استجابة من `*.supabase.co`.

**ما يحتاج Staging:** ترويسة الاستجابة الفعلية من Storage/CDN.

1. اطلب رابطًا موقّعًا جديدًا عبر الـResolver.
2. افحص الترويسات دون تنزيل المحتوى الكامل:

```bash
curl -sSI "<SIGNED_URL>" | grep -i "cache-control\|expires\|pragma\|age\|cf-cache-status"
```

3. افتح الرابط في تبويب جديد مع فتح DevTools ثم Network، وسجّل `Cache-Control` و`cf-cache-status` (أو ما يعادلها) وحالة `Size` (disk cache / memory cache).
4. أعد تحميل الصفحة وتأكد من عدم إعادة استخدام الرابط القديم بعد انتهاء صلاحيته.

**القبول:** ألا تكون الاستجابة قابلة للتخزين المشترك، وأن يظهر الرابط كطلب شبكة جديد عند إعادة العرض بعد الانتهاء. إن أظهر المزود ترويسة قابلة للتخزين، تُسجَّل كملاحظة FAIL جزئية وتُناقش المعالجة (إلغاء مسار fallback المباشر أو ضبط `cacheControl` عند الرفع) قبل Production.

**النتيجة:** `NOT RUN`.
